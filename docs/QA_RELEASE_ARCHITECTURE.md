# Review、测试与发行架构

本文件是代码评审、QA、构建、发布、重试和镜像的唯一规则源。核心原则是：评审发生在功能完成后，测试只在确有需要或正式发行时发生，构建器不隐式触发测试。

## 三条主路径

### 日常修改

```text
修改 → 人工/Agent Review → 修正 Review 问题 → 提交并推送私有 main
                                      └→ 按需本地生成 Current（零自动测试）
```

- 每次代码修改完成后都审查实际差异、边界、安全和可维护性。Review 默认只读代码，不运行测试。
- Reviewer 发现具体风险时，可以明确要求一项有针对性的检查；这属于开发修正，不属于发行步骤。
- Current 用于马上进行人工体验。`npm run release:local` 只在本机从当前已提交源码构建 Current，不执行源码 QA，不执行烟雾测试，也不下载云端产物。

### 正式发行

```text
                       ┌→ 本机构建并替换 Current（零自动测试）
版本提交和标签就绪 ────┤
                       └→ 一次正式 QA → 一次构建/烟雾 → 私有 Release
```

- `npm run release` 默认云端发行，并同时启动本地 Current 构建；两条路径互不下载、互不替代。
- 补丁版和次版本默认执行受影响的 `targeted` QA，主版本执行 `full` QA。稳定 Release 禁止选择 `none`。
- 正式 QA 使用 `--base previous-release` 覆盖上一祖先版本标签至目标提交的完整范围，不能只比较最后一条提交；首次发行以空树为基线覆盖全部源码。日常手动 QA 的范围不变。
- 云端 QA、构建和发布是三个可单独重试的作业。`resume_run_id` 直接复用一天内的已验证构建附件，不重跑 QA 或构建。
- 云端构建调用本地构建器时显式加 `--smoke`，因此正式云端产物只做一次最小隔离启动；Current 不继承该烟雾测试。

### 云端故障与本地兜底

1. 先修复云端配置、权限或服务问题，再对同一失败作业重试一次。
2. 如果 QA 和构建已成功而上传失败，只重跑发布作业；必要时用原 `run_id` 恢复云端附件。
3. 云端确实无法继续时才使用 `--mode local`。传入已有 `--resume-run RUN_ID` 时，本地入口确认该运行的 QA 作业成功后直接复用；没有可用云端 QA 凭据时，本地入口只执行一次正式 QA。
4. 本地构建器随后只生成 Current、ZIP 和安装程序，不再运行 QA。附件存在且提交、版本、摘要一致时直接复用，只补传缺失附件。

## QA 与构建边界

| 动作 | Review | 源码 QA | 产物烟雾 | 构建 |
|---|---:|---:|---:|---:|
| 日常代码完成 | 必须 | 默认无 | 无 | 无 |
| 本地 Current | 复用已完成 Review | 无 | 无 | 本地一次 |
| 正式云端 Release | 复用已完成 Review | 一次 | 云端产物一次 | 云端一次 |
| 本地正式兜底 | 复用已完成 Review | 复用云端；无凭据时本地一次 | 不重复 | 缺失时本地一次 |
| 公开 GitHub / CNB 镜像 | 发行说明 Review | 无 | 无 | 无 |

`scripts/qa-plan.js` 仅供正式 QA 或 Reviewer 明确点名检查时使用。测试组为 `release`、`mirrors`、`packaging`、`archive`、`catalog`、`data`、`desktop`、`mcp` 和 `safety`。失败可用 `--test-file` 或 `--group` 只重跑失败项。不得在 Current、本地打包、公开镜像或 CNB 镜像中隐式调用它。

## Windows 宿主、GitHub 凭据与网络

- 本机 Windows 凭据库是 GitHub 私有仓库访问的凭据来源。GitHub CLI 与 Git Credential Manager 必须指向同一有效账号；令牌不得写入仓库、日志或长期环境变量。
- 本机所有 Git 写操作和 GitHub CLI 远端操作，从第一次调用起使用正常 Windows 宿主凭据上下文。Agent 直接申请对应命令的宿主权限，不先在已知沙箱账户试错；授权被拒绝时停止，不修改 ACL、不改用其他账户或令牌路径绕过。只读本地状态、差异和纯产物校验仍可在沙箱进行。
- 发布入口只做一次轻量检查：在宿主上下文调用目标仓库 API。已知 Windows 沙箱账户由入口在调用 GitHub 前拒绝并说明原因，不自行提权；检查通过才派发、查询或上传。云端继续使用 workflow 注入的短期 GitHub Token，不改用本机凭据。
- 不执行 `gh auth login` 或搜索令牌位置。访问检查将网络/TLS、凭据和仓库权限错误分开报告；EOF、连接重置或超时不能称为令牌丢失。直接标签查询只在 HTTP 404 时回退草稿列表，网络、认证和格式错误不触发额外列表查询。
- 凭据检查成功后发生的 404、422 或权限错误按 API/工作流配置故障处理，不能误判为需要再次登录。
- 本机 Git/GitHub 默认直连，不写入或自动恢复代理，不把 Git 的代理配置注入 GitHub CLI，也不关闭证书校验。若直连失败，仅检查用户当前明确配置的网络路径并报告；更换代理须用户确认。CNB 默认由公开 GitHub Actions 镜像，无需本机 CNB Token 或上传。

## 状态、检查点与重试

- 本地启动器在派发前读取 Release 状态并处理幂等结果；云端不再设置独立预检或状态作业，只保留 QA、构建和发布。
- 本机检查点位于仓库外 `HamsterArchiver-Local/builds/release-runs/<version>-<commit>.json`。源码 QA、依赖、构建、烟雾、ZIP、安装程序和各发布目标各自记录。
- 网络、超时和 5xx 最多原地重试一次；响应不明确时只回读一次远端状态。断言、配置、权限、422 和摘要冲突立即停止并先修复根因。
- 同一根因第二次仍失败时停止本次任务并报告；禁止第三次派发、重新登录、重新构建或重新上传。
- 子 Agent 默认安静执行。只在完成、需要用户授权/输入、范围发生变化或确认无法继续时回报；协调者用一次长等待接收结果，不高频询问阶段状态。

## 分发不变量

1. 私有 Release 从版本提交生成四个附件：ZIP、安装 EXE 和两份 SHA-256。
2. 公开 Release 下载并逐字节校验私有正式 Release 的四附件，使用累积双语正文后镜像，零测试、零构建。
3. CNB 从公开正式 GitHub Release 镜像相同标签、正文和四附件，零测试、零构建。
4. Release 附件、公开源码快照和 CNB 标签是独立状态；其中一项成功不能替代另一项确认。
